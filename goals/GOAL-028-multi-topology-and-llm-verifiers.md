## 1. 背景与演进动因

目前 mush 采用的是经典的 **“雪橇领航制”（Hierarchical / Lead-Dog Pattern）**：
`人类 (Owner) ➔ 头犬统筹/派发 (Lead Dog) ➔ 工作犬执行 (Worker Dogs) ➔ 头犬初审 (Review) ➔ 人类终审 (Gate)`

### 现有架构的成就与瓶颈
1. **优势**：责任链路清晰，预算收敛可控，状态机与哈希链留痕完备；
2. **瓶颈（Relay Tax）**：所有任务与回执均由头犬中转，多层上下文存在压缩与失真；
3. **自我印证偏差（Confirmation Bias）**：若派发者与审核者为同一种认知模型（或单一头犬），容易产生同质化盲区；
4. **形态单一**：缺乏根据任务性质（如“确定性代码工序” vs “高风险安全决策”）动态切换组织结构的能力。

## 2. 核心架构设计

未来框架演进由 **四大组织拓扑** 与 **LLM-as-a-Verifier 独立验证体系** 共同构成：

```
                    ┌─────────────────────────────────────────────────────────┐
                    │            mush 看板：组织架构模式选择器                 │
                    │        (Organization Topology Selector)                 │
                    └───────────────────────────┬─────────────────────────────┘
                                                │
         ┌───────────────────┬──────────────────┴────────────────┬───────────────────┐
         ▼                   ▼                                   ▼                   ▼
 🌲 模式 A: 雪橇领航制   ⛓️ 模式 B: 工序流水线制             ⚖️ 模式 C: 对席陪审辩论制 🏷️ 模式 D: 悬赏竞标市场制
 (Hierarchical Sled)    (Sequential SOP Relay)             (Committee / Debate) (Bounty / Contract Net)
  • 头犬统筹拆解         • Spec (ZCode)                      • 生成犬 (Claude)    • 任务池公开发布
  • 工作犬分头执行       • Code (Claude)                     • 辩友犬 (DeepSeek)  • 按负载/价格自动竞标
  • 头犬集中汇总         • Test (Pi)                         • 仲裁犬 (Kimi)      • 异构犬抢单并发吞吐
  • 适用：大型探索目标   • 适用：标准化代码研发              • 适用：高风险重大决策• 适用：海量松耦合任务
```

### 一、 人类可选择的四大组织拓扑（Topology Modes）

#### 1. 🌲 模式 A：雪橇领航制 (Hierarchical / Lead Dog)
- **运行逻辑**：保留当前经典机制。头犬具备全局视野，负责接收任务、拆解分发、追踪会话、汇总报告；
- **适用场景**：大型探索性目标（如跨模块重构、架构探索、多工作区编排）。

#### 2. ⛓️ 模式 B：工序流水线制 (Sequential SOP / Assembly Line)
- **运行逻辑**：将任务标准化解构为**不可逆工序卡**，各犬依据物理特长专精单一工序：
  `需求规格卡 (ZCode) ➔ 核心实现卡 (Claude) ➔ 自动化测试卡 (Pi/AGY) ➔ 防御审计卡 (DeepSeek)`
- **工件流转**：工序间仅传递结构化工件（Spec Markdown / Git Patch / Test Output），阻断无关上下文冗余；
- **适用场景**：明确规格的代码实现与重构，极致节省 Token 与减少幻觉。

#### 3. ⚖️ 模式 C：同行对席辩论与陪审制 (Multi-Agent Committee / Debate)
- **运行逻辑**：引入多犬对席辩论机制：
  1. **提出**：生成犬（如 Claude）产出技术实现方案与代码；
  2. **挑刺**：异构审查犬（如 DeepSeek）独立审查，出具反对意见与漏洞列表；
  3. **交叉反驳**：双方在限定轮次内进行对席辩论，收敛共识；
  4. **合议呈交**：输出包含共识与分歧点的独立报告，呈交人类一锤定音。
- **适用场景**：最高红线治理（CONSTITUTION.md）、安全敏感变更、架构分歧仲裁。

#### 4. 🏷️ 模式 D：任务池悬赏市场制 (Bounty Market / Contract Net Protocol)
- **运行逻辑**：
  1. 任务池（Task Pool）公开发布未领取的 Task 卡与上限预算；
  2. 系统结合**四级可调度信度（GP-37）、实时会话成本（GP-33）与模型特长画像**自动竞标撮合；
  3. 支持工作犬之间自主发包与分流，实现多犬高并发吞吐。
- **适用场景**：海量独立单元测试编写、批量文件修复、异步批处理。

### 二、 LLM-as-a-Verifier 独立验证犬体系

借鉴 `LLM-as-a-Verifier` 范式，建立**生成与验证物理隔离**的严密防线：

```
                    ┌────────────────────────┐
                    │  生成阶段 (Generator)  │
                    │  工作犬产出代码/工件   │
                    └───────────┬────────────┘
                                │
                                ▼
  ┌────────────────────────────────────────────────────────────────────────┐
  │                    🛡️ LLM-as-a-Verifier 验证矩阵                      │
  ├──────────────────────┬─────────────────────────┬───────────────────────┤
  │ 🔒 安全验证犬        │ 📐 契约规格验证犬        │ 🧪 机检验证执行器     │
  │ (Security Verifier)  │ (Spec Verifier)         │ (Machine Verifier)    │
  │ • 检查密钥泄露       │ • 检查是否偏离 Task 目标 │ • 运行 `node --test`  │
  │ • 检查转义与注入     │ • 检查 API Schema 破坏  │ • 检查 0 失败、覆盖率 │
  └──────────────────────┴─────────────────────────┴───────────────────────┘
                                │
                                ▼
                    ┌────────────────────────┐
                    │  人类审批卡 (Owner)    │
                    │  双绿放行 / 驳回熔断   │
                    └────────────────────────┘
```

1. **核心铁律**：**生成者永不得自审（`Generator !== Verifier`）**，彻底切断模型自身的自我印证偏见；
2. **多视角切片验证（Multi-Facet Verifiers）**：
   - **安全验证者**：专注审查命令注入、密钥暴露、Windows 转义缺陷（DEF-07/08）；
   - **契约规格验证者**：严格比对修改范围是否越权，是否改写不可变决策（DECISIONS.md）；
   - **客观机检验证者**：以 `node --test` 与 AST 静态分析作为物理证据基石。

## 4. 验收与治理规格

1. **测试基线**：所有测试运行器严格使用 **`node --test`**（Node 内置，零额外三方依赖）；
2. **红线恪守**：无论选择何种拓扑模式，人类最高否决权与每单审批卡（D30）铁律不可动摇；
3. **零外网红线**：所有辩论、流水线与验证完全在本地多 Harness 间闭环，零数据外流。
